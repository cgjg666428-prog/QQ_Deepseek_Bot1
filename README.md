# QQ_Deepseek_Bot1

一个 Python + NapCat + DeepSeek 的 QQ 聊天机器人学习项目，记录本地部署、调试和功能整合的经历。机器人程序和 NapCat 运行在本机；模型请求发送到远端 API。


## 整体工作方式

这个项目把 QQ 消息、模型接口和本地记忆连接起来。NapCat 负责与 QQ 交互，Python 负责处理消息，DeepSeek API 负责生成回答。

```text
用户发 QQ 消息
    ↓
NapCat 将消息转换为 OneBot 事件
    ↓ 正向 WebSocket：Python 主动连接 NapCat，接收事件
qq_deepseek.py 判断私聊、群聊 @、图片或视频链接
    ↓
读取相关聊天历史 → 请求模型 API → 保存文字记录
    ↓ HTTP：Python 调用 NapCat 的发送消息接口
NapCat 将回答发回 QQ
```

HTTP 和 WebSocket 在这里承担不同任务：WebSocket 接收消息事件，HTTP 发送回复。两个地址都应与 NapCat 的实际配置一致。

## 当前代码包含什么

- 私聊文本回复；群聊通过 @机器人触发。
- 按私聊用户、群和群成员区分的 SQLite 历史；`/clear` 清理当前对话。
- 消息去重；可配置的随机插嘴，发布版默认关闭。
- 群聊图片输入接口，以及抖音链接下载、默认六张关键帧和后台处理逻辑。
- 视频下载与抽帧可独立测试；下载服务的支持状况可能变化。

限制：图片与视频画面理解需要 API 和模型实际支持图像输入；本次没有验证服务端能力。私聊的普通图片未接入看图分支。视频只有抽帧，没有语音识别。好感度、成就和长期人物记忆未实现。程序没有自动重连保障；文本 API 调用仍可能阻塞消息处理。这里存在功能代码不代表此次已完成端到端验收。

## 部署过程（Windows PowerShell）

下面按组件的依赖关系整理部署过程，方便理解和复现，不是完整的逐日操作日志。原环境已进行部署和调试；本次发布副本仅完成文档整理、基础秘密扫描、语法和离线检查，没有重新进行真实 QQ / 付费 API 的端到端验收。

### 1. 准备 Python 环境

安装 Python 后，在解压的项目文件夹中打开 PowerShell。建议使用 Python 3.11 或更新版本

```powershell
python --version
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
```

虚拟环境让这个项目的依赖与其他 Python 项目分开。后面的命令直接使用虚拟环境里的 Python，因此不需要另外执行激活脚本。

依赖与功能的对应关系如下：

| Python 库 | 在项目中的用途 |
| --- | --- |
| `openai` | 通过兼容接口调用模型；库名不代表本项目使用 OpenAI 模型 |
| `requests` | 调用 NapCat 的 HTTP 发送消息接口 |
| `websocket-client` | 连接 NapCat 的正向 WebSocket，接收 QQ 事件 |
| `python-dotenv` | 从本地 `.env` 加载配置 |
| `yt-dlp` | 尝试解析并下载抖音视频 |
| `opencv-python` | 读取视频并抽取画面 |

`sqlite3`、`json` 等是 Python 标准库，不需要另外用 pip 安装。

### 2. 创建本地配置，先验证模型接口

```powershell
Copy-Item .env.example .env
```

该命令用于首次配置；已有 `.env` 时不要覆盖自己的设置。在本地编辑 `.env`，不要把真实值填进 `.env.example`。

| 配置名称 | 应填写的内容 |
| --- | --- |
| `DEEPSEEK_API_KEY` | 自己的模型服务密钥 |
| `DEEPSEEK_BASE_URL` | 所使用服务的 API 基础地址 |
| `DEEPSEEK_MODEL` | 服务账户实际支持的模型名称 |
| `BOT_QQ` | NapCat 当前登录的机器人账号 QQ 号 |
| `NAPCAT_HTTP`、`NAPCAT_WS` | NapCat 的 HTTP 与正向 WebSocket 地址 |
| `NAPCAT_TOKEN` | 与 NapCat 两个服务保持一致的 Access Token |
| `RANDOM_REPLY_CHANCE` | 随机插嘴概率；发布副本默认 `0`，表示关闭 |
| `DOUYIN_COOKIES_FILE` | 可选 Cookie 文件路径，不使用时留空 |

```powershell
.\.venv\Scripts\python.exe test_deepseek.py
```

如果终端收到一条模型回答，说明这次文字 API 请求成功。这一步不会连接 QQ，但会调用付费接口。先把模型单独测通，之后机器人报错时就能更容易区分模型问题和 QQ 连接问题。

### 3. 配置 NapCat 的消息通道

另行从 [NapCatQQ 官方仓库](https://github.com/NapNeko/NapCatQQ) 获取 NapCat，按所安装版本的文档完成安装和 QQ 登录。本仓库不附带 NapCat、QQ 客户端或登录数据，也不固定某一版本的界面操作位置。

在 NapCat 中启用 OneBot HTTP 服务和**正向 WebSocket 服务**：

- HTTP 默认地址为 `http://127.0.0.1:3000`，用于发送回复。
- 正向 WebSocket 默认地址为 `ws://127.0.0.1:3001`，用于接收消息。
- 为两个服务设置 Access Token，并将同一值写入本地 `NAPCAT_TOKEN`；发布副本通过 Bearer 请求头认证。

修改端口后同步更新 `.env`，并确认 `BOT_QQ` 与实际登录账号一致。只允许本机访问这些端口，核对 NapCat 的实际监听地址。此项目是 Python 主动连接 NapCat，不使用反向 WebSocket 的接入方式。

原部署中，`qq_test.py` 用于单独观察事件。如果收到事件但主程序不回复，可继续检查触发条件和模型调用；如果连事件都收不到，应先处理 NapCat 服务、地址或认证。这个旧脚本不在发布包中，发布版直接通过主程序进行连接检查。

### 4. 启动主程序，先检查文字聊天

保持 NapCat 在线，再运行：

```powershell
.\.venv\Scripts\python.exe qq_deepseek.py
```

连接成功后，主程序会打印启动提示。只在你授权的私聊或群中测试：私聊直接发送文字，群聊发送“@机器人 + 问题”。默认关闭随机插嘴，因此没有 @ 的普通群消息不会触发回复。

主程序会提取消息文字、检查是否是自己的消息、判断触发条件，再把请求发送到模型。得到回答后通过 NapCat HTTP 接口发回 QQ。修改 `.env` 或代码后，先按 `Ctrl+C` 停止 Python 程序，再重新启动；同一机器人避免重复启动多个主程序，以免重复回复。

### 5. 加入 SQLite 对话记忆与消息去重

当前版本在主程序初始化时创建 `doo_memory.db`，通过 `save_message()` 保存用户消息和模型回答，通过 `get_history()` 读取最近记录供文字对话使用。默认读取最近 10 条消息记录，不是 10 轮完整对话。

私聊按用户区分；群聊按“群 + 群成员”区分，所以同一群中不同成员的历史不会使用同一个上下文键。数据库可在重启后保留记录，但这不等于实现了结构化人物记忆、好感度或成就系统。图片请求当前没有附加这些历史，只会在完成后保存文字记录。

私聊发送 `/clear`，或在群聊中“@机器人 + /clear”，可删除当前对话的数据库记录。数据库不需要手动建表，也不需要上传到 GitHub。程序还会在内存中记录已处理的消息 ID，减少重复事件引起的双回复；这份去重记录会在重启时清空，并不是永久去重保证。

### 6. 单独验证图片和视频处理，再接入主程序

群聊图片通过 `get_images()` 提取图片 URL，并由 `ask_deepseek_with_image()` 提交给模型。必须先确认所配置接口和模型接受图像输入；文字接口测通并不能证明看图可用。

视频增加了两个步骤：先下载，再抽帧。为便于定位问题，`video_test.py` 可以独立运行：

```powershell
# 先用自己的本地视频检查抽帧，不涉及网络下载。
.\.venv\Scripts\python.exe video_test.py --local "你自己的视频.mp4"
# 再检查抖音链接下载与抽帧。
.\.venv\Scripts\python.exe video_test.py "你有权访问的抖音分享链接"
```

测试结果保存在 `video_results/` 下的独立子目录中：下载模式保存视频，默认生成最多六张 `frame_*.jpg`，以及记录来源、帧位置和时间点的 `info.json`。使用 `--local` 时不会复制原视频，但记录中可能出现它的本地路径。

原部署的排查记录出现过下载器要求 `fresh cookies` 的错误，这属于下载阶段，不能靠修改 OpenCV 抽帧解决。遇到这种提示时，使用自己的 Netscape 格式 Cookie 文件：

```powershell
.\.venv\Scripts\python.exe video_test.py "你有权访问的抖音分享链接" --cookies "cookies.txt"
```

单独运行 `video_test.py` 不会自动加载 `.env`。在机器人中使用 Cookie 时，则在 `.env` 中设置 `DOUYIN_COOKIES_FILE`，再重启主程序。Cookie 是凭据，不能分享；有效 Cookie 也不能保证下载器支持所有链接。当前单文件下载配置不依赖 FFmpeg 合并，更换格式或下载器可能引入额外要求。

接入 QQ 时，主程序调用 `douyin_video.py`，后者在后台启动下载和抽帧子进程，一次最多处理一个视频，下载与抽帧超时为三分钟。抽出的图片转换为 Base64 data URL 后提交给图片接口，避免让远端服务读取本机磁盘路径。任务的临时文件随后清理。

使用方式是私聊发抖音链接，或群聊“@机器人 + 抖音分享”。均匀抽帧只能提供部分画面，不含音频，不能声称机器人已经听懂整段视频。

## 遇到问题时，从哪一层开始查

| 现象 | 优先检查 |
| --- | --- |
| `ModuleNotFoundError` | 是否给当前使用的虚拟环境安装了 `requirements.txt` |
| 提示找不到 API Key，或 `BOT_QQ` 相关错误 | `.env` 是否与主程序同目录，配置是否填写且格式正确 |
| 模型返回认证、模型不存在等错误 | 用 `test_deepseek.py` 分开检查密钥、服务地址和模型名称 |
| WebSocket 无法连接或认证失败 | NapCat 是否在线、正向服务是否启用、端口与 Token 是否一致 |
| 私聊正常，群聊无回复 | 是否 @了正确机器人；未 @ 时随机插嘴默认关闭 |
| 收到消息却发送失败 | HTTP 服务是否启用，其地址和 Token 是否匹配 |
| 文字正常，图片报错 | 服务是否支持图像消息、当前模型是否有视觉能力、图片 URL 是否可访问 |
| 视频下载失败 | 先单独运行 `video_test.py`，根据下载器报错检查链接支持、网络和 Cookie |
| 视频抽帧成功，但无法解释画面 | 图片接口是否接受多张 Base64 图像；检查模型响应 |
| 重复回复或回复很慢 | 是否同时运行了多个主程序；检查重复事件、随机插嘴及接口等待时间 |

查看终端和 `video_last_error.txt` 有助于定位错误，但公开求助前应先遮挡凭据、QQ 号、群号和聊天内容。

## 数据与隐私

对话内容会发送到所配置的模型 API，并写入本地 `doo_memory.db`；控制台也会打印账号、消息及部分错误。群聊使用前说明这些处理方式并取得参与者同意。图片 URL 或视频关键帧可能发送到模型服务。随机插嘴也会处理群消息，默认关闭。发布截图前遮挡账号、群号、聊天内容、头像、Cookie、Token 和二维码。

`.env`、数据库、Cookie、下载结果、日志和备份已被排除。`.gitignore` 只防止新文件被加入，不能清除曾经提交的秘密。如果凭据曾被上传、公开截图或分享，应先撤销并重新生成，再处理仓库历史。不要依赖删除最新版本来解决泄露。
